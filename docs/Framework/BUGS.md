# Framework bug register

Defects of the TauFW Framework (`Framework/`), found while planning the recipe IO work (R4, October 2026, branch
`Refactor-2025`) by reading the source. A bug is fixed when the **Fix** column names the part that fixed it.

Policy: until the refactor is finished, bugs are registered only (no fixes); each fix comes later in its own commit.
**Output impact** describes the change for a user of `taufw.py` (and for the BBB case `framework.production`,
which records `run.json`).

**Severity:** **crash** (raises on a reachable path), **wrong** (silently wrong), **latent** (the code is wrong but
nothing reaches it in normal use).

| ID | Location | Symptom | Severity | Fix | Output impact |
|---|---|---|---|---|---|
| K01 | `python/framework.py` `_context`, `python/run_record.py` `RunRecord.load` | A run directory that is moved or copied is loaded with its new location (`run_dir` comes from where `run.json` is), but the artifacts of its `DONE` stages in `run.json` keep the old absolute paths. The next stage then reads the files at the old location: silently if they still exist (a copy, or `cp -r` and both copies advanced), or it fails while its commands run if they do not. The fit's preflight does not catch it, because it checks the shapes on disk only when no stage of the run makes them (`stages/fit.py` `preflight`). | latent | registered only (moving runs belongs to the deferred disk/EOS work) | |
| K02 | `python/framework.py` `_advance_stages` (manifest written before `run.json` is saved), `Utilities/python/Process/_outdir.py` `output_dir_problems` | If the process stops after a stage's `manifest.json` is written and before `run.json` is saved, the stage is still `NEW` in `run.json`, but its output directory is no longer empty (it holds the manifest). The next `advance` stops in preflight with "output directory ... is not empty" until the directory is removed by hand. The comment there says such a crash "only repeats the stage", which is not true for the local stages. A later input that names this directory by path would also accept it, since only a `DONE` stage has a manifest. | latent | registered only | |
| K03 | `python/stages/local.py` `advance` (`last_status.inputs`), `python/stages/plots.py`, `python/stages/histograms.py` | The `tuples` input slot selects no data: plot.py and createinputsTES.py always read the tuples through `$PICODIR` of the run's PicoProducer configuration, and `inputs.tuples` (a production stage, or `null`) is only recorded. If the configuration's `$PICODIR` is not where that production stage wrote, the stage reads other tuples than the ones its input names, and `run.json` lists the named ones. | wrong (design limit) | CL §18 step 6: plots and histograms get the pattern of the tuples their input names (`--tuples`), from the production stage's artifacts or `{external: ...}`; `null` keeps the old behaviour (old recipes only) | none for `null`; with a production input the scripts read the production stage's tuples instead of `$PICODIR` |
| K04 | `python/stages/production.py` `_merge` (artifacts are `TupleArtifact.to_dict()`), `python/step_runner.py` `StepContext.input` | The tuple artifacts of a production stage have no `kind` key (the artifacts of every other stage have one, e.g. `kind: shapes`). A filter by kind therefore finds none: in a python step `ctx.input('<production id>', kind='tuples')` returns an empty list, and so does `StageContext.input_artifacts('tuples', kind='tuples')`. Nothing filters tuples by kind today. | latent | registered only | adds `kind: tuples` to the production artifacts in `run.json` and `manifest.json` (BBB `framework.production`) |
